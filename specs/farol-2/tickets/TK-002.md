# TK-002 — Expandir contratos fundamentais para Farol 2.0

## Objetivo e limites

Adicionar envelopes e identidades v2 para projeto de conhecimento, revisão,
operação, capacidade e migração, mantendo leitores 1.x.

Não inclui: IR detalhada, RAGFlow real ou remoção dos schemas antigos.

## Leitura em ordem

1. `docops/contracts.py` → `validate_contract` — validador canônico.
2. `docops/api_types.py` — resultados públicos atuais.
3. `docs/CONTRACT-COMPATIBILITY.md` — política expand–contract.
4. `schemas/project.schema.json` e `schemas/result.schema.json` — formas existentes.

## Decisões já resolvidas

- V2 é contrato novo; leitores 1.x continuam durante expansão.
- Mercado Livre/curso/página não entram nos novos enums.
- Liberdade local: nomes internos; IDs e outcomes públicos seguem a especificação.

## Mapa de alterações

- Existente: `schemas/`, `docops/schemas/`, `docops/contracts.py`, `api_types.py`.
- Novo: schemas `knowledge-project-v2`, `operation-v2`, `migration-v2`, `capability`.
- Fora: schemas 1.x e `docops/master.py` nesta fatia.

## Contrato técnico

- Entradas: JSON v2 com schema/revision/idempotency/expected revision.
- Saídas: outcome tipado, revisão, blockers, próxima ação.
- Invariantes: unknown fields fora de `extensions` falham; segredo/conteúdo não entra.
- Erros: schema/version/revision/idempotency conflict distintos.
- Compatibilidade: validadores 1.x permanecem; cópias de schema sincronizadas.

## Exemplos de aceite

- **AC-001/003**: request v2 incompleto → `needs_input` apenas para decisão material.
- **AC-002**: mesma key/payload → mesma identidade; payload diferente → conflito.
- **AC-027**: migration plan aponta source version e nunca muta origem.
