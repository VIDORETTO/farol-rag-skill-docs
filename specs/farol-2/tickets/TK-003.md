# TK-003 — Criar KnowledgeBackend e encapsular o legado

## Objetivo e limites

Introduzir a Interface profunda `KnowledgeBackend` e mover o comportamento atual
para `KnowledgeRagLegacyAdapter` sem alterar resultados 1.x.

Não inclui: RAGFlow, novo ranking ou remoção do legado.

## Leitura em ordem

1. `docops/retrieval.py` → `RetrievalAdapter`, `McpRetrievalAdapter`.
2. `docops/rag_sync.py` → `RagSynchronizer`.
3. `docops/runtime.py` → discovery/provenance knowledge-rag.
4. `tests/test_rag_sync.py`, `tests/test_evaluator.py`, `tests/test_reader_sessions.py` → comportamento existente.

## Decisões já resolvidas

- Interface usa `probe/prepare/apply/query/snapshot/discard/close`.
- Complexidade MCP/processo fica no adapter; não expor primitives do vendor.
- Testes observam raiz/CLI; internos apenas para protocolo externo controlado.

## Mapa de alterações

- Novo: `docops/backends/base.py`, `legacy_knowledge_rag.py`.
- Existente: tornar `retrieval.py`/`rag_sync.py` consumidores ou facades.
- Fora: `skills/vendor/knowledge-rag` sem alteração.

## Contrato técnico

- Entradas/saídas: DTOs v2 imutáveis e resultados 1.x adaptados.
- Invariantes: adapter não escolhe direitos/revisão; close encerra só filho criado.
- Erros: capability, auth/config, unavailable, timeout e protocol drift distintos.
- Idempotência: prepare/apply reconciliam identidade; query é read-only.

## Exemplos de aceite

- **AC-020**: fake controlado e adapter legado satisfazem a mesma contract suite.
- **AC-021**: snapshot não usa ID externo como identidade do pacote.
- **AC-022/023**: indisponível/auth falha tipada e redigida.
